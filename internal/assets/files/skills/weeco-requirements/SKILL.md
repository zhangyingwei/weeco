# weeco：需求澄清

澄清只回答“做什么、为什么、不做什么、怎么算成”，不回答“怎么做”。
“怎么做”由设计团队给出；老板只提问、复述、定边界。

## 入口

- 没有 requirement，或用户刚提出一个新需求。
- 先运行 `weeco status`，确认没有正在处理的同一需求。

## 选模式

- **快速澄清**（默认）：需求边界清楚，3–5 个问题能收敛。
- **方向发散**：客户已有候选方向，需要排除。老板可以基于客户提供的信息和已有认知帮比较，不查外部证据；需要证据时转调研。
- **方向未知**：客户说“不知道做什么好”。不要自己列方向，先建“方向调研”需求，再招 research 团队（见下）。

发散不是设计：不比较技术方案、不画架构、不估工时。

## 需求甄别

清晰不等于成立。先判断这个需求是否值得做，再把它写进简报。

三问，对应三类失真：

| 类型 | 判别问题 | 结论 |
|---|---|---|
| 假需求 | 它推进哪个上游目标？不做会影响什么？ | 与目标无关、背离，或只增加复杂度 |
| 伪需求 | 预期收益是什么？成本多大？有没有更直接的路径？ | 看起来好，实际收益低或有反作用 |
| 错误需求 | 前提依据是什么？谁验证过？ | 前提与事实不符 |

结论只有五种：真需求 / 待验证 / 假需求 / 伪需求 / 错误需求。
没有证据时只能写“待验证”，不要凭感觉下结论。

怎么引导：

- 假需求：指出它与上游目标的关系，给出“不做、改写、缩小”三个选项。
- 伪需求：要求定义可观察的收益和最小验证；成本明显高于收益时建议调整。
- 错误需求：先核实事实，不进入设计。
- 老板不替客户否决；摆出证据、影响和选项，客户做最终决定。

证据不足，或需求是 S1、影响面大时，招调研团队（仍在需求阶段）：

```bash
weeco team recruit --requirement R-... --purpose research \
  --contract docs/weeco/contracts/R-...-research.md --size N
```

N 按工作图定：把每个问题集当工作单元，画依赖、数并行链；B 等 A 的结论就是同一条链；高风险且还没有独立的人时加一条验证链。见 `weeco-boss` 定员。

调研合同写清楚：要回答的问题、可用来源、时间盒、证据要求、禁止改代码、只写报告。
团队产出：事实核查、目标对齐、效果与成本、替代方案（含“不做”）、建议与置信度。
老板验收后把结论写回简报，再和客户决定：继续 / 调整 / 先验证 / 关闭。

## 调研边界

老板可以做：

- 问客户要事实、资源、偏好。
- 读项目现状：文件、git、`weeco status`。
- 单次检索核对一个可一句话回答的外部事实，并标明来源。

老板不可以：

- 多次检索、多来源比对、竞品/市场/政策/收益分析。
- 用单次检索下“真/伪需求”的最终结论；仍不确定就只能写“待验证”。
- 估算成本、工时，或比较技术方案。

越过边界就停手：写“待验证”，招 research 团队。结论必须有来源、有证据、有置信度。

## 方向未知

客户说“不知道做什么好”时，方向本身就是待调研的问题。

1. 先问上游目标、可用资源、约束；这些是客户能回答的。
2. 建一个“方向调研”需求：

```bash
weeco requirement new --goal "确定<领域>的方向"
```

3. 写调研合同，招 research 团队：

```bash
weeco team recruit --requirement R-... --purpose research \
  --contract docs/weeco/contracts/R-...-research.md --size N
```

N 按工作图定：每个独立问题集是一条链，依赖链不拆人；S1 或决定“做/不做”且还没有独立的人时，加一条验证链。定员依据写进合同。

4. 团队产出 3–5 个方向，每个方向给证据、成本、风险、最小验证。
5. 客户选定方向，把最终目标写进简报。方向与调研 goal 差异大时，新建产品需求，关闭调研需求。

老板不自己列方向、不自己查市场。

## 必答清单

按顺序问，一次只问 1–3 个最影响范围的问题：

1. 目标：客户最终要拿到什么结果？
2. 使用者与场景：谁在什么情况下用它？
3. 范围：这次必须包含什么？
4. 非目标：这次明确不做什么？至少写一条。
5. 验收直觉：客户怎么判断“成了”？要可观察，不要“更好用”。
6. 约束：时间、兼容、数据、部署、合规、必须复用的东西。
7. 风险等级：S1 / S2 / S3，见下。
8. 待设计决定：澄清中冒出的“怎么做”问题，全部记到简报里，不在这里回答。

## 清晰度门禁

四条都满足才能建产品需求；方向未知时先建调研需求，不受此门禁限制。

1. 能用 3 句话复述目标、范围、非目标，客户确认“对”。
2. 非目标非空。
3. 验收直觉是可观察的结果，不是形容词。
4. 甄别结论已记录；结论为“待验证”时，客户已确认风险，或调研团队已给出结论。

不满足就继续问。问不出来时，把不确定项写成“待客户确认”，不要替客户假设。

## 落盘

1. 从 `~/.weeco/templates/requirements.md` 复制需求简报：

```text
docs/weeco/requirements/R-YYYYMMDD-NN.md
```

2. 建需求，`--goal` 只放一句话摘要：

```bash
weeco requirement new --goal "..."
```

3. 把阶段设为设计，设计合同引用简报路径：

```bash
weeco requirement stage R-... --set design
```

4. 加载 `weeco-design`。

需求变更时，追加到简报的“变更记录”，重新过一遍受影响的必答项；不改历史。

甄别结论为假需求或错误需求时，建议客户关闭需求：

```bash
weeco requirement close R-...
```

理由和依据留在简报里，不进入设计。

## 风险等级

| 等级 | 判定 | 后续 |
|---|---|---|
| S1 | 安全/权限/密钥、数据删除或迁移、支付、公共 API/契约、生产发布、跨模块核心改动、客户指定 | 设计合同写“强制独立 review”；实施后招只读 review 团队 |
| S2 | 多模块、有兼容或回滚要求、依赖外部服务 | 老板在验收时决定是否加独立 review |
| S3 | 单模块、可回滚、影响面清楚 | 常规验收 |

## 可以跳过设计吗

可以，但要有理由，并记录阶段：

```bash
weeco requirement stage R-... --set plan
# 或
weeco requirement stage R-... --set implement
```

澄清不能跳；小需求用快速澄清。

## 不要

- 不要给方案、架构、技术选型、工时估算；这些记入“待设计决定”。
- 不要在需求没确认前招设计/实施团队；调研团队除外。
- 不要自己写代码。
- 不要把用户的每一句话都扩写成需求；先确认目标。
- 不要在客户没确认时把简报标成“已确认”。
- 不要在证据不足时把需求判成“真需求”；写“待验证”或招调研团队。
- 不要用单次检索下真伪结论；不确定就待验证 + 调研团队。
- 不要自己列产品方向、做市场/竞品调研。
- 不要加载通用 brainstorming/设计 skill；weeco 项目内的需求流程以本 skill 为准。
- 不要替客户做产品决定；老板给证据和选项。
