# weeco 团队工作模型

本文描述 weeco 组织团队、拆分任务、派发、开发和验收的操作规则。

**实现状态**：v0.12.2 已实现 `--level`、等级模型候选、画师角色、`config init/check` 和 `accept`。自动回归覆盖这些路径；真实 Herdr 冒烟尚未执行，画师出图能力需要在真实环境单独确认。UI 原型确认是 Skill 层约定，CLI 不会自动识别 UI 或强制询问。

---

## 1. 角色

| 角色 | 是谁 | 能做什么 | 不能做什么 |
|---|---|---|---|
| 老板 | 用户 | 提目标、定验收边界、决定是否接受 | 不直接管理成员 |
| 负责人 | 当前 Herdr 会话 | 拆任务、招募、派发、参与执行、整合、验收、返工、关闭 | 不能把自己的验收责任转给作者 |
| 工程成员 | 真实 Herdr agent pane | 按任务和 turn 执行、提交报告 | 不能招募、不能验收、不能关闭团队 |
| 画师 | 固定以 Codex 启动的成员 | 完成图像类交付物并报告 | 不能验收、不能关闭团队 |

负责人是唯一有招募和关闭权的角色。资深成员也不例外。

## 2. 等级

等级只回答“任务要多强、多贵”，不回答“做什么领域”。领域写在 `role` 里。

| 等级 | 判断标准 | 典型任务 |
|---|---|---|
| 资深工程师 `senior` | 需求不全需要自己澄清；跨模块；根因不明；要做方案设计；后果不可逆或代价高；负责最终独立验收 | 架构设计、疑难调试、大范围重构、数据迁移方案、高风险验收 |
| 中级工程师 `mid` | 需求明确；改动局限在一个模块或接口；有现成模式可循 | 常规功能实现、接口开发、代码审查、联调 |
| 初级工程师 `junior` | 机械、单文件、规则明确、有明确样例可照做 | 改配置值、重命名、格式化、按模板补测试、文档措辞 |
| 临时工 `temp` | 只为产生一次性信息或动作，没有可复用交付物 | 探查、复现问题、跑命令、格式转换、信息汇总 |

### 定级顺序

按顺序问，命中即停：

1. 后果是否不可逆或代价高（数据迁移、线上变更、安全、对外发布、最终验收）？是 → `senior`。
2. 是否需要跨模块判断、根因定位、方案设计或长上下文？是 → `senior`。
3. 边界是否清晰、改动是否局限在一个模块或接口、是否有现成模式？是 → `mid`。
4. 是否机械、单文件、规则明确、几乎不需要判断？是 → `junior`。
5. 是否只是一次性信息或动作？是 → `temp`。

拿不准定 `mid`，在任务文件里写明不确定点。定级看“难度 × 错误代价”，不看任务字数。任务字面小但结论对外负责，升档。

所有任务都要核验。等级不是验收豁免券。

## 3. 任务拆分

### 拆分单位

一个子任务必须同时满足：

1. 有一个可独立检查的交付物（文件、接口、报告、素材）；
2. 有一个明确的负责人；
3. 有一条具体的核验标准。

不满足就继续拆。按交付物切，不按“前端/后端/测试”切。

### 拆分步骤

1. 写清最终交付物和验收标准。
2. 列出能独立验收的交付物，一个交付物一个负责人。
3. 给每个交付物定级（第 2 节）。
4. 标注是否为画师任务（第 4 节）。
5. 标注依赖和共享文件归属。
6. 决定合并还是独立派发（第 5 节）。
7. 依赖不清或需要用户决定时，先派 `temp` 探查，或只暂停依赖该决定的工作。

### 示例

| 任务 | 拆分与定级 |
|---|---|
| 预览端口 5186 改 5187，验收能启动 | 改动 `junior`；启动核验 `temp`。负责人自己做或派一名初级，加一名检查者 |
| 写 200 字活动通知，缺失信息留空 | 成稿 `junior`；事实与字数核对 `mid`（对外发布，错误代价高） |
| 新增 JWT 登录接口并测试 | 接口实现 `mid`；测试 `junior`；独立审查 `mid`；联调 `temp` |
| SQLite 迁移 Postgres，可回滚 | 迁移方案 `senior`；脚本 `mid`；演练 `temp`；数据独立核验 `senior` |
| 做一张带文案和二维码的海报 | 背景图派画师（Codex）；文案/二维码合成 `junior`；成图检查 `temp` |
| 查线上接口 500 | 复现与定位 `temp`；需要改代码升 `mid`；跨服务根因升 `senior` |
| 批量替换文档旧术语 | 替换 `junior`；抽样核对 `temp` |

### 画师任务标注

画师不是独立的能力系统，而是固定以 Codex 启动的成员。需要生成图片时，派一名画师即可，不额外配置图像模型或调用命令。

标记为画师任务：

- 交付物包含无法用代码或文本生成的位图：海报背景、插画、封面、照片质感素材；
- 找不到可用的现成授权素材。

以下内容不交给画师，交给 `junior` 做确定性生成或合成：

- 图表、二维码、截图、精确排版文字、产品界面、事实性示意图。

视频暂不纳入。

混合任务继续拆。例如“带确定文案和二维码的活动海报”拆成：背景图（画师，Codex）＋ 文字/二维码合成（`junior`）＋ 成图检查（`temp`）。

## 4. 派发

### 等级对应派发方式

| 等级 | 派发方式 |
|---|---|
| `senior` | 独立负责一个大任务，不和其他大任务合并；可拆出机械部分给 `junior` 并行 |
| `mid` | 一名成员；同一模块、同一文件区的 1–2 个任务可合并 |
| `junior` | 多个互不共享文件的机械任务可合并给一名成员，减少启动开销 |
| `temp` | 负责人自己做，或临时派一名成员并行；不为它保留长期成员 |

同一文件不派给两个并行成员。必须共享时，指定唯一写者，另一方只读或串行等待。

### 复核配对

| 作者等级 | 复核要求 |
|---|---|
| `junior` | 默认由 `mid` 以上复核 |
| `mid` | 独立同级复核即可；高风险事项升到 `senior` |
| `senior` | 高风险结论由另一名 `senior` 独立核验 |

常规小改动不必层层签字，负责人抽查实际产物即可。

### 模型候选

每个等级在配置文件里列一组候选模型，按顺序失败转移。用户只写模型、agent 和强度，其他由 weeco 决定：

```json
{
  "levels": {
    "senior": [
      { "model": "<资深模型名>", "effort": "high" },
      { "agent": "codex", "model": "<另一个资深模型名>" }
    ],
    "mid": [
      { "model": "<中级模型名>", "effort": "medium" }
    ],
    "junior": [
      { "model": "<初级模型名>", "effort": "low" }
    ],
    "temp": [
      { "agent": "pi", "model": "<临时模型名>" }
    ]
  }
}
```

- `model` 必填；`agent` 省略时默认 `claude`；`effort` 省略时按等级取内置默认（资深 high、中级 medium、初级和临时 low）。
- 一个等级可以写单个对象或数组；数组顺序就是失败转移顺序。
- 策略、重试次数、冷却时间、超时都用内置默认，不出现在用户配置里；需要临时覆盖时用命令行参数。
- 只在一轮工作开始前的启动失败时转移：命令不存在、模型不可用、未登录/欠费、进程立即退出。
- `agent_pane_busy`、工作区信任提示、模态向导不换模型，直接报错让负责人检查。
- 一轮工作开始后的失败不自动换模型。成员报 `--blocked` 后，由负责人决定 `send` 返工或 `start --replace --level ...` 换人。
- 记录实际选中的等级、候选、agent 和失败尝试。正式验收用 `--model` 固定模型。

### 画师

画师是内置角色，启动时 Agent 固定为 `codex`，不参与等级的模型候选选择，也不需要在配置里单独指定图像模型。画师使用 Codex 的默认模型和强度；`--level` 对画师无效，传了直接报错，避免误以为换了模型。

```bash
weeco start --name illustrator --role artist --task /abs/poster-brief.md
```

- 凡是需要生成图片的任务，直接派画师，等价于启动一个 Codex 成员。
- 画师的任务文件里写清用途、风格、尺寸、必须出现和禁止出现的元素、版权与使用范围、输出目录。
- 画师的产出由负责人或 `junior` 按第 6 节检查实际文件；画师不能验收自己的成果。
- 精确文字、二维码、图表仍交给 `junior` 合成，不用画师生成。
- 画师没有额外权限：不能招募、不能验收、不能关闭团队。

`role artist` 是内置映射；用户配置里不需要出现画师相关字段。

## 5. 开发过程

### 工作区选择

- 小型任务：单文件/单模块、无迁移、验收快，直接在当前 checkout 修改。
- 中大型任务：跨文件/模块、新功能、多人并行、数据迁移/发布/安全/不可逆操作，使用 Herdr worktree。
- 不确定时按中大型处理或问用户。

worktree 必须在第一个 `weeco start` 之前创建，通过 `--dir` 和 `--team-pane` 指定；`--dir` 是成员工作目录，`--team-pane` 是 worktree 的 root pane，成员会从它分屏并出现在 worktree workspace，负责人留在原 workspace。已有 run 后不能切换目录或团队 pane。worktree 从 HEAD 创建，不包含未提交改动；脏工作区先让用户决定提交、stash 或直接在当前树做。已在 linked worktree 中时直接使用，不再嵌套。交付前在 worktree 内执行 `git status --porcelain` 和 `git branch --show-current`，报告路径、分支、workspace 与未提交文件；是否合并、保留或删除由用户决定。删除前确认没有未提交改动，或用户明确接受丢失，再执行 `herdr worktree remove --workspace <id>`；有未提交内容时不能自动 `--force`。`weeco close` 只关闭成员，不删除 worktree；不要用 `workspace close` 代替清理。

### UI 原型

涉及用户可见界面、布局、视觉、交互、响应式或深色模式时，负责人先确认是否需要原型；这是默认直接开工的例外。

- 需要：原型作为独立交付物，放 `docs/prototypes/<feature>/`；只写静态原型、关键状态、交互和 `notes.md`，不写生产 UI、不接真实后端。复杂流程用 `senior`，简单组件可用 `mid`。负责人检查、用户确认后，用 `accept` 记录；UI 实现任务引用原型路径。
- 不需要：记录用户决定，任务写清布局、状态、交互、窄屏和深色模式等 UI 验收标准。
- 非 UI 工作可以并行；UI 实现等待原型确认；原型被否时只返工原型。

### 任务文件

每个成员一份任务文件，至少包含：

```text
目标：
等级：
角色：
UI 范围：
是否需要原型（用户确认）：
原型路径：
是否画师任务（是则 Agent 固定为 Codex）：
原始材料位置：
负责的产物或文件：
依赖：
交付位置：
核验标准：
可操作边界：
共享文件归属：
```

任务文件和共享契约放在项目内稳定路径（例如 `.weeco/tasks/`）或任务指定位置。`/tmp` 只适合可丢弃的临时文件；多个任务共享的契约不能只引用 `/tmp`，必须能在项目目录或 run 目录中找到副本。`weeco start` 只会把 `--task` 指向的单个任务文件复制进 run 目录，不会自动复制任务里引用的共享文件。

### 负责人操作

```bash
weeco start --name coder --role "实现后端" --level mid --task /abs/backend-task.md
weeco status
weeco status checker --wait --timeout 60
weeco send coder --file /abs/follow-up.md
weeco close coder
weeco close
```

- 首次 `start` 自动建立 run。记下 run ID；需要显式定位时加 `--run ID`。
- `start` 会确认成员真正进入 `working`。未确认时保留 pane，检查后重试或取消，不当作启动失败清理。
- `send` 给成员开新 turn。成员仍在 `working` 时拒绝发送。
- `close` 保留负责人 pane。未提交的成员不能正常关闭，只能 `--cancel --reason`。

### 成员执行

- 只改负责范围内的文件或资源，保留他人的改动。
- 任务只要求方案、计划或草稿时，以该交付物为终点，不执行其中的真实操作。
- 修改问题前说明原因和修法。
- 只有会改变行动的缺口才向负责人提问。
- 不递归招募，不调用 `/weeco` 改变角色，不修改信任或权限设置。

### 轮次与报告

```bash
weeco report --run <id> --turn N --file /abs/report.md
weeco report --run <id> --turn N --file /abs/blocked.md --blocked
weeco send lead --run <id> --file /abs/question.md
```

- 必须使用收到的明确 turn。旧轮次报告会被拒绝。
- 新一轮必须做新一轮的工作并单独报告，不能复用旧报告。
- `send lead` 只通信，送达不代表负责人或用户批准。
- 报告后等待返工或关闭。

### 等待

- `status --wait` 一次只等一轮：新报告到达、出现 `missing/replaced/blocked`、或超时后返回。
- `idle`、无输出、超时都不代表完成。
- 超时后核对 pane 和任务进展，不反复轮询。

## 6. 验收

负责人必须读实际交付物和原始来源，不能只读成员的完成声明。

### 按交付物类型核验

| 交付物 | 核验方式 |
|---|---|
| 代码 | 针对当前版本运行测试、构建、实际启动或 HTTP 联调；检查改动文件 |
| 文档/事实 | 每条结论回查原始材料位置；核对字数、缺失项、对外表述 |
| 方案/计划 | 检查约束、步骤、对账方式、回滚、失败重跑、未验证依赖 |
| 图片 | 打开实际文件；检查尺寸、精确文字、二维码；核对提示词、实际使用的模型和生成参数 |

方案完整不能证明生产操作已执行。模拟检查不能冒充真实用户反馈。

### 独立检查

有独立检查价值时，让检查者从原始要求和证据重新核验，并尝试找反例。另一名作者重复同一结论、或换角色签字，都不算独立。

检查深度按错误代价调整：

- 低风险小改动：负责人抽查实际产物；
- 常规功能：作者自查 + 负责人实测；
- 高风险或对外结果：独立检查者按第 4 节配对规则核验。

### 返工

发现问题时，写清：

- 现象；
- 期望；
- 依据（原始要求或实测结果）；
- 修复边界。

用 `send` 给相应成员开返工轮。负责人也可以修复自己负责的部分，修改后重查受影响结果。

### 验收记录

规划项 `weeco accept --turn N --file /abs/accept-note.txt` 记录：

- 核验了哪些产物；
- 实际执行的命令或观察；
- 未验证项；
- 剩余问题。

它只留痕，不改变流程，也不代替负责人判断。

### 关闭

- 交付边界内检查完成、必要返工完成后，说明交付位置、实际验证、未验证项和剩余问题，再 `close`。
- 使用 worktree 时，`close` 前报告 worktree 路径、分支、workspace 和 `git status`，询问用户保留还是删除；用户未决定前不删除。删除用 `herdr worktree remove --workspace <id>`，有未提交内容时不得自动 `--force`。`close` 本身不删除 worktree。
- `close` 不是验收通过的证明。
- 仍待用户决定或仍需返工时，保留成员。
- 取消使用 `close --cancel --reason "原因"`，不用取消结果冒充完成。

## 7. 配置

### 位置与优先级

```text
内置默认 < ~/.weeco/config.json < <项目>/.weeco/config.json < 命令行参数
```

没有配置文件时使用内置默认值，行为与当前版本一致（Claude 成员、不额外指定模型）。

### 用户可配的内容

只有一类：每个等级的模型候选。画师固定用 Codex，不需要额外配置。其余字段一律由内置默认值决定，`config check` 会显示最终生效结果。

```json
{
  "levels": {
    "senior": [
      { "model": "<资深模型名>", "effort": "high" },
      { "agent": "codex", "model": "<另一个资深模型名>" }
    ],
    "mid": [
      { "model": "<中级模型名>", "effort": "medium" }
    ],
    "junior": [
      { "model": "<初级模型名>", "effort": "low" }
    ],
    "temp": [
      { "agent": "pi", "model": "<临时模型名>" }
    ]
  }
}
```

模型名按本机 CLI 实际支持的名字填写；上面的占位符不是有效值。

### 校验

加载配置时必须检查：

- `--level` 指向存在的等级；缺某个等级时给出警告并使用内置默认；
- 每个等级至少一个候选；
- 候选的 `agent` 只能是 `claude/codex/pi`；
- 模型名非空；
- `effort` 只能是内置允许的取值。

未知字段必须报错并指出字段名，不能静默忽略。文件缺失时使用内置默认；文件存在但非法时直接报错，不带着错误配置运行。

`weeco config init` 生成最小模板，`weeco config check` 输出解析后的等级、候选和实际模型。

### 命令行

```bash
weeco config init
weeco config check
weeco start --name checker --role "独立核验" --level senior --task /abs/check.md
weeco start --name coder --role "实现后端" --level mid --model <中级模型名> --task /abs/backend.md
weeco start --name illustrator --role artist --task /abs/poster-brief.md
weeco accept --turn 2 --file /abs/accept-note.txt
weeco status --json
```

`status` 显示每个成员的等级、角色、实际候选和 agent。`config check` 输出示例：

```text
senior: 2 candidates → <资深模型名> (effort=high), <另一个资深模型名> (fallback)
mid:    1 candidate  → <中级模型名> (effort=medium)
junior: 1 candidate  → <初级模型名> (effort=low)
temp:   1 candidate  → <临时模型名> (effort=low)
```

## 8. 硬规则

1. 按交付物拆任务，不按岗位拆。
2. 同一文件不并行写；共享文件指定唯一写者。
3. 定级看难度和错误代价，不看字数；拿不准定 `mid`。
4. 所有任务都要核验；`junior` 产出默认由 `mid` 以上复核。
5. 高风险或对外结果由 `senior` 独立核验。
6. 精确文字、二维码、图表、界面截图不用生成式模型。
7. 失败转移只发生在启动阶段；一轮内失败由负责人决定返工或换人。
8. 成员不递归招人；负责人不把验收外包给作者。
9. `idle`、超时、“已完成”文字都不构成验收证据。
10. 关闭不是验收通过；取消结果不能冒充完成。
